## 1. 目标与完成定义

近期定位为：面向一个可信运维团队的节点纳管与维护作业实验平台，可在普通 Linux 主机、容器或虚拟机上独立运行。

主场景固定为：

**登录 → 发现或登记实验节点 → 人工批准 → 确认资产及目标 → 执行 SSH 维护任务 → 查看真实结果与审计 → 故障后核对和恢复。**

第一个任务采用无破坏性的系统信息采集或健康检查。后续维护动作由实际团队需求决定，不先建设通用工作流引擎。未取得用户需求时，以此参考任务完成作品交付，并将“真实需求已验证”保持为待完成。

本阶段有两个独立出口：

| 出口 | 必须交付 | 完成标准 |
|---|---|---|
| A：可交付的技术作品 | 固定版本软件环境、可重复演示、真实执行与故障证据、准确文档 | 新环境按文档完成主流程；关键反例通过；不存在把 mock 当真机或把启动当完成的描述 |
| B：团队试用 | 一个明确场景、实际使用者反馈、访问与凭据边界 | 使用者独立完成任务，记录实际收益与限制；没有使用者时保持待验证，不阻塞 A |

不以购买硬件、获得真实 BMC、真实 GPU 或通知服务 secret 作为出口 A 的条件。出口 A 完成后可以转入维护，不要求为了持续开发而开启下一阶段。

## 3. 当前证据与待复现事项

下表来自代码路径审视与已有验收记录，不是本计划已经完成的运行测试。Claude 应先在当前代码复核；已有修复不得重复覆盖。

| 项目 | 基线证据 | 本阶段处理 |
|---|---|---|
| 部署仍未闭环 | runbooks/deployment.md 的 2026-10-10 记录列出认证入口、IP 变化后注册、Shell 失败、回调异常等未通过项 | 接续现有修复；区分新旧代码与旧日志 |
| 容器启动被视为作业完成 | satellite/pkg/docker/executor.go 启动后返回；cmd/satellite/handler.go 立即上报 COMPLETED | 启用该模式前必须等待实际结果；未修复时明确禁用该入口 |
| 取消只改数据库状态 | JobResource.cancelJob 写 CANCELLED；未沿该路径下发终止命令 | 明确取消语义，不能显示已终止而远端仍运行 |
| 断连时派发或回报只记日志 | StreamRegistry.sendCommand、Satellite sendStatus | 交付与回报必须有持久化状态或明确可追溯失败 |
| 状态可被迟到回调覆盖 | JobExecutionService 直接写回调状态，缺少完整转换约束 | 明确终态、尝试身份及乱序处理 |
| 调度未计入存量占用 | SchedulingService / PartitionedSchedulingService 每次只装载新任务 | 活跃入口必须满足资源互斥；实验能力不能因标签而绕过检查 |
| GPU 描述超过当前约束 | LcmConstraintProvider 未包含 GPU 型号和 IB Fabric 约束；派发缺可行性拒绝 | GPU 暂停对外承诺，未支持的需求明确拒绝 |
| 租户字段未构成隔离 | JobResource 使用请求 tenantId；QuotaService 检查未见主路径调用 | 首阶段限制为单团队，不宣称多租户隔离 |
| 运行镜像缺少执行依赖 | Shell 调用 bash；SSH 调用本地 ssh；Satellite runtime Dockerfile 未显式配齐这些依赖 | 按保留执行方式验证最终镜像，不只验证开发机 |
| 现有测试范围有限 | 浏览器套件使用 API mock；load-test 为 200 个模拟 Satellite 的短时注册/心跳；BMC 为 fixture | 保留现有回归，补真正执行和恢复证据，不写万级生产结论 |

调度节点目前代表 Satellite 执行端，而 SSH payload 另含远端目标。首批设计必须说明两者关系，避免将执行端 CPU/GPU 当成远端机器的资源证明。

## 4. 范围与默认选择

### 4.1 必做范围

- 一个明确的 Linux + Docker Compose 参考环境，单 Core，1～3 个实验目标。
- 真实 Core、Satellite、PostgreSQL、Redis、Kafka 和前端；复用现有部署与 Demo 资产。
- 一个受支持的 SSH 执行路径，目标使用真实 sshd 和真实命令进程。既有 mock SSH 继续用于协议测试，不作为真实执行验收。
- 主流程浏览器联调，真实状态回调、审计和故障核对。
- 任务状态与派发正确性、必要的调度保护、最小访问与凭据边界。
- 一份可独立复现的演示及按证据划分的能力说明。

### 4.2 暂缓范围

- 真实厂商 BMC 准入、实体服务器 PXE、GPU/NVLink/IB 性能收益。
- 多 Core 高可用、多集群联邦、多租户商业化、万级扩容。
- 新执行器、新硬件厂商适配、通用流程设计器、UI 动效扩展。
- 为提高数字而扩大覆盖率、扩大负载规模。
- 为本阶段整体更换技术栈，或移除 Kafka / Redis / Timefold 后重写架构。

保留现有实现；实验标签需要实际入口限制支撑。不允许只在 README 写“不支持”，API 仍静默接受并执行。

### 4.3 环境与授权边界

- 本地实验使用独立服务名、端口、数据卷和实验凭据；清理只针对本计划创建的资源。
- 不覆盖当前 dev 环境、已有证书和个人文件；不对已有 compose 执行无范围的 down / down -v。
- SSH 目标必须限定为已批准实验资产；不允许请求随意指定任意地址并转成可信维护任务。
- 优先使用 key 与 known_hosts 校验；不把真实私钥或口令持久化进 Job、Kafka payload、日志或 Git。复用现有凭据解析机制，先核对适用性，不为此默认引入新的 secret 平台。
- 真实团队环境的部署、重启、网络探测和命令执行仍按用户实际授权范围进行。计划本身不授权访问任意企业资产。

## 5. 里程碑与实施顺序

建议首轮投入窗口为 2～4 周，这是复盘时间盒，不是交付所有内容的工期保证。按 M0 → M1 → M2 → M3 推进，M4 根据使用条件执行，M5 可选。每个里程碑拆成可审核的小批次，不能把整份计划一次性实现为大 PR。

### M0 — 固定基线与首批计划

任务：

1. 记录 HEAD、分支、dirty diff、未跟踪文件及已有验证结果；确认是否有其他会话正在修改。
2. 接续当前部署修复及已有本地审核交接，逐项确认哪些结论仍成立。不回退、不清理、不重新实现已有改动。
3. 为 M1 形成具体文件清单、行为变化、验证和回滚方案，依 AGENTS 的计划流程执行。用户若已明确批准该批实施，不重复索取同一授权。
4. 定义参考环境的版本、资源需求、端口及数据目录。首次安装允许下载依赖，离线制包复用已有工具，不另建发行体系。
5. 确定支持状态：SSH 为基准；其他执行模式和 Allocation API 逐项确认继续支持还是在实验环境禁用。

验收：基线可追溯，首批范围明确，现有工作得到保留。不能把“暂无测试环境”写为实现已经正确。

### M1 — 可重复部署与真实主流程

任务：

1. 关闭当前部署路径的已知阻断：启动、mTLS、前端代理与 healthcheck、运行镜像依赖。
2. 明确两类入口：本机实验可以显式启用开发认证并限定暴露范围；团队试用必须有正式身份来源和权限映射，不通过开启硬编码开发账号来冒充生产认证。团队认证作为 M4 门槛，不拖住实验作品。
3. 修复资产批准与 Satellite 身份恢复，使批准关系不会仅因容器 IP 变化丢失；身份依据必须经过认证核对，不能只换成客户端自报名称。
4. 用真实 sshd 执行一个只读任务，返回输出、退出码、目标和时间；前端能显示结果，审计能关联操作人、设备和任务。
5. 核对执行端与目标设备的关联；目标不得在提交到执行之间被任意替换。
6. 禁用参考环境不需要的 PXE / DHCP 监听或明确隔离，不让默认实验启动影响所在网络。

验收：

- 从干净数据和无隐式本机配置开始，按文档完成主流程；记录代码/镜像版本和环境。
- mTLS 正向通过；明文、无证书、不受信任证书在业务处理前明确拒绝，不能只用超时证明。
- 前端至少有一条连真实后端的浏览器验收；API mock 套件继续保留但单独标注。
- 同一身份重连恢复，未批准身份仍被拒绝。
- 当前部署阶段 Step 5 只在其原验收条件全部满足后关闭；本机实验通过不能代替该阶段的生产验收。

主要入口：现有 compose、Satellite Dockerfile、运行配置、注册服务、SSH executor、demo / ci_demo_smoke、前端 Jobs、部署 runbook。

### M2 — 任务正确性与故障恢复

先确定并记录状态转换与派发契约，再实现最小持久化机制；数据库迁移、proto/API 变化需要给出兼容和回滚说明。

任务：

1. 区分排队、派发、执行、执行终态和结果未知；可以扩展状态或附加字段，但 API、DB、前端、审计和指标语义必须一致。
2. 区分 Job、执行尝试和消息身份，阻止迟到回调覆盖新尝试或终态。验证回调来自预期执行端。
3. 消除数据库“已调度”与消息发送失败之间的静默缺口。优先评估在现有 DB 中持久化派发记录并重试，不引入新的消息基础设施。
4. 处理离线派发、送达确认、执行中断和回报补送。持久化只需支撑明确的恢复保证，不能声称任意外部操作 exactly-once。
5. 非幂等远程命令在执行结果不明时禁止自动重发。无法确认结果应进入可核对状态，由操作者确认后新建尝试。
6. 运行中取消只有收到实际停止证据才能认定执行已终止。SSH 连接关闭不保证远端进程终止；首版若不能保证，明确拒绝运行中取消或显示取消请求待确认。排队取消必须防止随后派发。
7. 设置有边界的超时和输出大小，避免无限任务或无限内存缓冲。超时不等于远端已停止。
8. 修复或禁用 Docker 的“启动即完成”；若继续支持，等待退出并保留真实退出码。其他保留模式遵循同一语义。
9. 对 Core、Satellite 重启后的任务进行核对，避免永久停在无解释的 SCHEDULED/RUNNING。
10. 审计至少覆盖提交、批准/拒绝、派发尝试、结果、取消/超时及人工核对动作；日志不得泄露执行凭据。

必要反例：

| 场景 | 验收要求 |
|---|---|
| 命令 exit 0 / 非零 | 分别成功/失败，退出码真实 |
| Docker 启动后非零退出（若启用） | 不提前 COMPLETED |
| 长任务超时 | 明确超时与远端执行是否仍未知 |
| 排队取消；运行中取消 | 分别验证未执行、真实停止或明确不支持；无伪成功 |
| 派发前断连 | 有持久化待处理或明确失败，不能只留日志 |
| 执行后回报断连 | 可补报或进入结果未知，不静默丢失 |
| 重复派发或重复回调 | 不盲目重复执行，不重复累计结果；跨进程恢复也验证 |
| 乱序或迟到回调 | 终态和新尝试不被旧消息覆盖 |
| Core / Satellite 重启 | 数据、任务和结果可核对，失败原因可追溯 |
| DB/Kafka 暂时不可用 | 持久化/消息错误对状态可见，恢复后无伪完成 |

验收以实际进程、真实依赖服务和可观察副作用为准。例如受控命令在实验目录写入唯一记录，用其证明执行次数；不能仅通过 mock 调用次数证明不重复执行。

### M3 — 调度边界与作品交付

调度只做正确性收口，不扩大算法目标：

1. 明确调度的是 Satellite 执行容量还是目标设备资源。首版 SSH 不承诺远端 GPU 分配。
2. 保留资源分配入口时，纳入已有占用，并使用原子预留/并发控制保证不同请求不争用同一资源；完成、取消和恢复时核对释放。
3. 不可行解禁止派发；无可用节点时明确等待或拒绝，并有后续处理，不能永久无说明。
4. 未支持的 GPU 型号、拓扑等条件明确拒绝。单租户边界需要 API 约束，不接受任意 tenantId 冒充其他租户。
5. Allocation 若保留，必须证明“仅分配”不会进入默认 Docker 执行路径；无法收口时禁用并说明。
6. 用不依赖真机的反例验收：一台 8 核节点同时接收两项各需 8 核的请求、无匹配型号、无可行节点、释放后再次请求、重启后已有占用。
7. 完成一条 5～10 分钟演示：成功任务、失败任务、一次断连或重启后的核对，以及证据边界。
8. 更新 README、DEMO_GUIDE、PROJECT_STATUS 和路线图：区分代码存在、fixture 回归、真实软件环境验收、虚拟硬件验收、实体硬件验收。
9. 在既有架构文档中解释关键取舍：为何单 Core、为何不自动重试未知结果、为何暂缓多租户与硬件承诺。避免新建重复架构报告。

出口 A 验收：

- 新环境按文档完成安装和演示，记录实际耗时与资源用量，不预设未经实测的性能承诺。
- M1/M2 必要场景通过，M3 中开放入口的约束通过。
- Core、Satellite 和整套环境重启后验证状态；至少一次备份恢复到独立实验实例，并检查任务/资产/审计一致性。
- 外部 SSH 目标的副作用不会随 DB 备份回滚；恢复后先核对，禁止根据旧队列盲目重放。
- 交付有版本对应关系的启动说明、验收摘要、已知限制及截图/短演示材料。截图不代替可重复执行证据。
- 技术作品可以完成；团队需求与真机支持仍按实际证据标记。

### M4 — 团队试用与需求验证

进入条件：出口 A 通过，有明确试用者，并取得目标环境操作授权。

任务：

1. 选择一项既有工作，如节点健康检查、配置核查、日志采集。先记录原方法、频率、人工步骤、失败处理和必须保留的审计内容。
2. 在试用前补齐实际身份来源、最小角色权限、资产范围、凭据保护和访问入口。检查禁用/过期身份与未授权目标的负向路径。
3. 让试用者独立操作一次，记录需要作者介入的地方、任务结果准确性、故障定位体验。
4. 对比原流程，记录实测收益与维护负担；不得编造节省时间或用户认可。
5. 根据反馈只做一轮必要改进，不自动扩大为工作流平台或资产管理全家桶。

没有试用者、真实任务或身份接入条件时，保持 M4 待验证，出口 A 转入低频维护。不要用代理模拟用户反馈替代真实反馈。

### M5 — 可选的虚拟 Redfish / PXE 实验

进入条件：出口 A 通过；硬件方向仍有明确学习或团队价值；宿主支持所需虚拟化与隔离网络。

- 先检查 KVM/libvirt/UEFI、可用内存和磁盘、网络隔离。条件不具备就跳过，不启动平台迁移。
- 使用现成 sushy-tools 动态模拟器和 1～3 台虚拟机，不自建庞大 BMC 模拟平台。
- 验证 Redfish 控制下的虚拟机电源变化，再选择一条 UEFI + iPXE + kickstart 路径。
- 装机成功以虚拟机重启后 OS 可访问、身份与资产可关联为准，不以模板返回 200 或启动日志为准。
- 使用可丢弃磁盘、隔离 DHCP 网络及固定依赖版本；记录下载大小、时长和清理步骤。
- 只登记虚拟环境证据，不向 hardware-acceptance/matrix.yaml 的真实机器列表写入 PASS。

参考：[sushy-tools 动态 Redfish 模拟器](https://docs.openstack.org/sushy-tools/latest/user/dynamic-emulator.html)。工具实际特性与宿主要求在实施时重新核对。M5 不属于首轮必交付项。

## 6. 验证、审核与交付方式

- 高风险改动先执行 CI Contract guard，再按 CI_CONTRACT 触发相应运行时矩阵。
- 跨子系统变更按 AGENTS 运行三个子系统的完整适用验证。不能用单测、静态 guard 或已有 CI 绿灯替代本轮验证。
- 复用既有 demo-smoke 和 Playwright 结构；需要新增运行模式时集中管理配置，避免第二套私有启动脚本。
- 故障实验只运行在本计划隔离环境，不对共享服务注入故障。
- 每项结果记录：代码 SHA/dirty diff、依赖与镜像版本、环境、命令、预期、实际、日志位置、未完成部分。
- 同一区分：本地测试、CI、发布镜像、文档部署验收、实际用户试用。通过其中一个不能自动关闭其他项。
- 本地实验产物放项目忽略目录，删除本轮不用的临时文件；密钥按仓库既定机制存放。
- Claude 完成一个实施批次后提供改动摘要、验证证据、已知风险和回滚口径，交 Codex 审核。代码审核不代替用户验收。
- 提交/推送/合并/发布依据当时的用户授权，不由本计划自动扩大权限。

## 7. 风险、取舍与停止条件

| 风险 | 处理 |
|---|---|
| 将全量可靠性改造塞进两周 | 先完成一种执行方式；不支持的能力明确禁用；窗口结束后按证据重新估量 |
| SSH 断连或超时后结果不明 | 保留未知状态与人工核对，不承诺外部副作用 exactly-once |
| 学习目标推动持续加组件 | 复用现有栈，新增依赖必须对应本阶段不可替代的需求 |
| 演示配置逐渐变成生产默认 | 实验覆盖显式限定，保留生产 TLS 和认证边界 |
| 原有部署修复与新阶段相互覆盖 | 先固定基线和关闭当前批次，再推进新行为 |
| 无真实用户反馈 | 完成作品出口，业务价值保持假设，不继续假设性扩展 |
| 没有 KVM 或硬件 | 完成容器/软件层交付，硬件阶段延期，不阻塞近期成果 |

每 2～4 周复盘一次：

- 核心流程可靠且有人试用：按具体反馈继续。
- 核心流程可靠但暂无试用条件：交付作品，进入维护。
- 大量时间仍用于安装与环境修补：继续收窄参考环境，不增加功能。
- 首轮未完成可靠执行：重估剩余工作，明确保留/禁用项，不以延长路线图掩盖失败。
- 真机到位后另开硬件验收批次，先一个型号、一个固件版本，不恢复全厂商并行扩张。
